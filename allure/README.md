# allure

Report metadata for the Allure report built from the Go test layers.

## Flow

There is no Allure plugin in the Go code. Every layer runs under
[gotestsum](https://github.com/gotestyourself/gotestsum), which writes JUnit
XML; Allure 2 imports JUnit XML natively.

```
gotestsum --junitfile allure-results/<layer>-<module>.xml \
          --junitfile-testsuite-name relative \
          --junitfile-testcase-classname relative \
          -- -shuffle=on ./...                   # one file per layer × module
scripts/allure-meta.sh allure-results          # + categories.json, executor.json
allure generate --clean --single-file -o allure-report allure-results
```

The e2e layer is the same: `cd e2e && gotestsum --junitfile … -- -tags e2e -count=1 ./...`.

What the report shows per test comes from JUnit: the suite (package), the
case (`TestX/sub_test`), status (pass / failed / skipped), duration, and on a
failure the test's full output as the trace (testify's `Error Trace:` /
`Error:` block, the e2e harness's dump of the child process output). There
are no steps, labels or links — name tests for what they check.

## Files

| File | What |
|---|---|
| `categories.json` | Failure buckets for the Categories tab, copied into the results by `scripts/allure-meta.sh`. First match wins, in file order. |

`executor.json` (who ran the suite: GitHub Actions / GitLab CI / local) is
generated by `scripts/allure-meta.sh` from the runner's variables, not kept
here.

## Categories and JUnit

gotestsum writes a failure as `<failure message="Failed">…test output…</failure>`,
so Allure's *message* is always the constant `Failed` and everything useful is
in the *trace*: the categories for failures match with `traceRegex`. A skip
puts the `t.Skip` reason into the skipped message, so the flake bucket matches
with `messageRegex`. JUnit has no "broken" status from gotestsum (every
failure is `failed`); both statuses are listed so the file also works for
results from other producers.

| Category | Matches |
|---|---|
| Quarantined flake | skipped, message mentions `flak` or a `GB-<n>` ticket (`t.Skip("flaky: GB-123 …")` — the flakiness policy) |
| Build / setup failure | `[build failed]`, `[setup failed]`, a panic, a `-timeout` hit |
| Infrastructure | Docker / testcontainers / Toxiproxy, connection refused / reset, i/o timeout, deadline exceeded, an e2e child that exited before ready or a missing binary |
| Product defects | a testify assertion (`Error Trace:` / `Error:`), `expected` / `actual`, an `Eventually` condition never satisfied |
| Skipped | any other skip (e.g. `-short`, no Docker locally, e2e data services without `E2E_*` URLs) |

Adjust the regexes when a real failure lands in the wrong bucket; keep the
order (the specific buckets before the catch-alls).
