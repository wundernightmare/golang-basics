# allure

Report metadata for the Allure report built from the Go test layers.

## Flow

Two kinds of results go into one report.

**JUnit** — the unit and integration layers and schemathesis. There is no
Allure plugin in their Go code: each runs under
[gotestsum](https://github.com/gotestyourself/gotestsum), which writes JUnit
XML, and Allure 2 imports JUnit XML natively. What the report shows per test
comes from JUnit: the suite (package), the case (`TestX/sub_test`), status,
duration, and on a failure the test's full output as the trace. No steps,
labels or links — name tests for what they check.

**Native** — the e2e suite, through [testo](https://github.com/ozontech/testo)
and [testo-allure](https://github.com/ozontech/testo-allure)
(`e2e/report_test.go`): a test case per scenario with its feature, the
sub-tests as steps with their own timings, and each service's output as an
attachment. It writes `*-result.json`, `*-container.json` and attachments
into `.reports/allure-native/<run>/`.

```
gotestsum --junitfile .reports/junit/<layer>-<module>.xml \
          --junitfile-testsuite-name relative \
          --junitfile-testcase-classname relative \
          -- -shuffle=on ./...                   # one file per layer × module
ALLURE_RESULTS_DIR=.reports/allure-native/e2e \
  go test -tags e2e -count=1 ./...             # in e2e/: native results (and JUnit, under gotestsum)
scripts/allure-collect.sh .reports/allure-results   # both kinds → one directory
scripts/allure-meta.sh .reports/allure-results      # + categories.json, executor.json
allure generate --clean --single-file -o allure-report .reports/allure-results
```

`allure-collect.sh` is what keeps the e2e tests from being counted twice: the
e2e job still writes a JUnit file (GitLab's merge-request widget reads it),
and a native directory `<run>` that holds results replaces
`.reports/junit/<run>.xml`. When the directory is empty — the suite did not
build, or died before its first test — the JUnit file is the only record and
stays in.

## Files

| File | What |
|---|---|
| `categories.json` | Failure buckets for the Categories tab, copied into the results by `scripts/allure-meta.sh`. First match wins, in file order. |

`executor.json` (who ran the suite: GitHub Actions / GitLab CI / local) is
generated by `scripts/allure-meta.sh` from the runner's variables, not kept
here.

## Categories

gotestsum writes a failure as `<failure message="Failed">…test output…</failure>`,
so for a JUnit result Allure's *message* is always the constant `Failed` and
everything useful is in the *trace*. A native result is the other way round:
the *message* is the assertion or `t.Fatal` text and the *trace* a Go stack.
Each failure bucket is therefore listed twice under one name — once with
`traceRegex`, once with the same expression as `messageRegex`. A skip puts
the `t.Skip` reason into the message in both kinds. JUnit has no "broken"
status from gotestsum (every failure is `failed`); both statuses are listed
so the file also works for results from other producers.

| Category | Matches |
|---|---|
| Quarantined flake | skipped, message mentions `flak` or a `GB-<n>` ticket (`t.Skip("flaky: GB-123 …")` — the flakiness policy) |
| Build / setup failure | `[build failed]`, `[setup failed]`, a panic, a `-timeout` hit |
| Infrastructure | Docker / testcontainers / Toxiproxy, connection refused / reset, i/o timeout, deadline exceeded, an e2e child that exited before ready or a missing binary |
| Product defects | a testify assertion (`Error Trace:` / `Error:`), `expected` / `actual`, an `Eventually` condition never satisfied |
| Skipped | any other skip (e.g. `-short`, no Docker locally, e2e data services without `E2E_*` URLs) |

Adjust the regexes when a real failure lands in the wrong bucket; keep the
order (the specific buckets before the catch-alls).
