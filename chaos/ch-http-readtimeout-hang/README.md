# Chaos-лаборатория: зависание clickhouse-go сверх `ReadTimeout`

Отдельный Go-модуль вне `go.work` (собирается с `GOWORK=off`), обёртки драйверов из
репозитория не используются: только `github.com/ClickHouse/clickhouse-go/v2` v2.51.0
и `github.com/jackc/pgx/v5` v5.12.0.

## Гипотеза

> При выставленном `ReadTimeout` клиент clickhouse-go в режиме HTTP может зависнуть
> намного дольше `ReadTimeout`, если с соединением что-то случилось.

**Подтверждена.** В HTTP-режиме `Options.ReadTimeout` попадает только в
`http.Transport.ResponseHeaderTimeout` (`conn_http.go`, `createHTTPRoundTripper`).
Он ограничивает ожидание заголовков ответа и больше ничего:

| фаза запроса | чем ограничена в HTTP-режиме | чем ограничена в нативном протоколе |
|---|---|---|
| установка соединения | `DialTimeout` | `DialTimeout` |
| запись тела запроса (INSERT) | ничем | ничем (дедлайна на запись нет) |
| ожидание заголовков ответа | `ReadTimeout` | `ReadTimeout` (дедлайн на каждое чтение) |
| чтение тела ответа | ничем | `ReadTimeout` (дедлайн на каждое чтение) |

Без дедлайна в `context` зависание в «ничем не ограниченных» фазах длится столько,
сколько позволит TCP — см. замеры ниже.

## Стенд

```
реплика A ─┐                       ┌─> PgBouncer 1.24 (transaction pooling, без таймаутов) ─> Postgres 18.6
реплика B ─┴─> Toxiproxy 2.12 ─────┤
                                   └─> ClickHouse 25.8 (HTTP 8123 / native 9000)
```

Образы — уже имевшиеся локально (`postgres:18.6-alpine`, `clickhouse-server:25.8-alpine`,
`toxiproxy:2.12.0`). Образа PgBouncer локально не было: он собран из локального
`alpine:3.22` через `apk add pgbouncer` (`infra/pgbouncer.Containerfile`).

Клиент во всех тестах: `ReadTimeout=2s`, `DialTimeout=2s`, пул из одного соединения.

Сбои:

| имя | что имитирует |
|---|---|
| `toxi-timeout`, `toxi-timeout-down` | данные перестают идти, TCP-соединение остаётся установленным |
| `toxi-bandwidth` | канал деградировал до 1 КБ/с |
| `toxi-reset`, `toxi-down` | RST / закрытие соединения (контроль: быстрый отказ) |
| `nft-drop`, `nft-drop-in` | настоящая потеря пакетов (nftables DROP на loopback), в обе стороны / только ответы |
| `ch-pause` | процесс ClickHouse заморожен (`podman pause`), ядро продолжает отвечать ACK |

## Запуск

```sh
./infra/lab.sh up
export GOWORK=off GOFLAGS=-mod=mod
go build -o bin/ ./cmd/...

./bin/chmatrix matrix -out out/matrix                       # HTTP, 148 случаев, ~8 минут
./bin/chmatrix matrix -proto native -out out/matrix-native  # то же по нативному протоколу
./bin/trivial split                                         # как часто заголовки и тело приходят раздельно
./bin/trivial hang -mode stall -op select1 -cap 2m          # SELECT 1, обрыв между заголовками и телом
./incident.sh nft-drop stream 50 0                          # воспроизведение инцидента
./incident.sh nft-drop stream 30 5s                         # то же с дедлайном на итерацию
./incident.sh nft-drop stream 30 0 true                     # то же с chfix
./bin/chmatrix matrix -fix -ctx none -out out/matrix-http-fix  # HTTP-матрица с chfix
./infra/lab.sh down
```

`nft-drop*` требуют `sudo nft` (правила живут в отдельной таблице `inet chaoslab`,
`lab.sh down` её удаляет).

## Результаты

Все цифры — от момента сбоя до возврата из вызова, контекст без дедлайна
(`context.Background()`), если не сказано иное. Сырые данные: `out/matrix/results.md`,
`out/matrix-native/results.md`, `out/matrix-http-fix/results.md`, `out/long/*.json`, `out/incident-*.txt`.

### 1. Матрица «операция × сбой» (148 случаев на протокол, потолок наблюдения 45 с)

Результаты `clickhouse.Open` и `database/sql` совпали во всех случаях, поэтому столбец один.

| сбой | операция | HTTP | native |
|---|---|---|---|
| нет (контроль) | `SELECT sleep(3)` — медленные заголовки | 2,0 с, ошибка | 2,0 с, ошибка |
| нет (контроль) | первый блок сразу, затем паузы по 3 с | 6,0 с, успех (`ReadTimeout` не сработал) | 2,0 с, ошибка |
| любой | `SELECT 1`, новое или прогретое соединение | ≤ 2,1 с | ≤ 2,0 с |
| `toxi-reset`, `toxi-down` | любая | ≤ 0,2 с | ≤ 0,2 с |
| `toxi-timeout*` | потоковый SELECT (сбой посреди тела) | 11 с | 1,5–1,8 с |
| `toxi-timeout*` | большой INSERT | 2,1–2,3 с | 2,1–2,3 с |
| `toxi-bandwidth` | потоковый SELECT | **висит > 45 с** | 1,5–1,8 с |
| `nft-drop`, `nft-drop-in` | потоковый SELECT | **висит > 45 с** | 1,7 с |
| `ch-pause` | потоковый SELECT | **висит > 30 с** | 1,7 с |
| `toxi-bandwidth`, `nft-drop*`, `ch-pause` | большой INSERT (48 МБ) | **висит** | **висит** |

Итого без дедлайна зависли 16 из 74 случаев по HTTP и 8 из 74 по нативному протоколу
(только INSERT). С дедлайном 5 с в контексте не завис ни один случай ни в одном
протоколе, максимум 5,0 с.

Стек зависшего HTTP-чтения: `net/http.(*bodyEOFSignal).Read` ← `clickhouse-go/v2.(*capturingReader).Read`.
Стек зависшей записи: `net/http.(*persistConn).writeLoop` в `net.(*conn).Write` (HTTP),
`internal/poll.(*FD).Write` (native).

### 2. Сколько на самом деле длится зависание (потолок наблюдения 25 мин)

| сценарий (HTTP) | результат | чем закончилось |
|---|---|---|
| потеря пакетов посреди тела ответа | 153 с (76 × `ReadTimeout`) | `read: connection timed out` — TCP keep-alive Go по умолчанию (15 с + 9 × 15 с) |
| потеря пакетов во время записи INSERT | 951 с (475 ×) | `write: connection timed out` — ретрансмиты ядра (`tcp_retries2=15`) |
| канал 1 КБ/с во время записи INSERT | > 25 мин, не вернулся | — |
| посредник молчит, но держит TCP (тело `SELECT 1`) | > 25 мин, не вернулся | — |
| потеря пакетов, TCP keep-alive выключен (тело `SELECT 1`) | > 12 мин, не вернулся | — |

Часы зависания получаются только в двух последних строках: keep-alive либо выключен,
либо на него отвечает кто-то между клиентом и ClickHouse (балансировщик, сайдкар, NAT).
Для сравнения: системный `tcp_keepalive_time` на хосте — 7200 с.

### 3. Тривиальный запрос (`cmd/trivial`)

- `SELECT 1` и DDL-пустышка зависают, если соединение пропадает между заголовками
  ответа и телом: заголовки получены, `ReadTimeout` своё отработал, тело читается без
  ограничения.
- ClickHouse отправляет заголовки и тело раздельно: в ~20 % из 2000 ответов они пришли
  отдельными чтениями, зазор — медиана 9–13 мкс, максимум 87 мкс. Окно узкое, то есть
  событие редкое, но оно существует на каждом запросе.
- Тот же обрыв на нативном протоколе (после первых 4 байт ответа): `i/o timeout` через 2,0 с.
- Пул из одного соединения во время зависания: `clickhouse.Open` отдаёт второму запросу
  `acquire conn timeout` через `DialTimeout` (2 с); `database/sql` без дедлайна ждёт
  соединение в `database/sql.(*DB).conn` бесконечно — второй `SELECT 1` тоже зависает.
- Побочное наблюдение (один прогон): `Exec` DDL при потере пакетов после заголовков
  вернул `nil` через 153 с, хотя тело ответа не дочиталось.

### 4. Воспроизведение инцидента (`incident.sh`, `cmd/svc`)

Реплика: pgx-пул из одного соединения к PgBouncer, clickhouse-go HTTP с пулом из одного
соединения, воркер берёт `pg_advisory_xact_lock` и под ним читает из ClickHouse без
дедлайна; `/readyz` — `SELECT 1` в обе базы через те же пулы с таймаутом пробы 1 с.

`./incident.sh nft-drop stream 50 0` — потеря пакетов на пути реплики A к ClickHouse в
момент чтения тела ответа:

- A: процесс жив, фаза `ch-stream` все 50 с наблюдения, readiness = false по обеим базам
  (оба единственных соединения заняты зависшей итерацией);
- Postgres: блокировка у A, сессия `idle in transaction`, возраст транзакции растёт;
- B (её сеть исправна): висит в `pg-wait-lock`, readiness = false по Postgres —
  зависание одной реплики через блокировку останавливает и вторую;
- после снятия сбоя обе реплики вернулись в работу в пределах 8 с.

`./incident.sh nft-drop stream 30 5s` (дедлайн 5 с на итерацию): A отпускает блокировку,
B остаётся готовой и продолжает работу; A не готова только по ClickHouse.

`./incident.sh nft-drop insert 40 0` зависание **не** воспроизвёл: сбой попал до
заголовков ответа, клиент падал через 2 с и отпускал блокировку. Зависание возникает
только когда обрыв попадает в фазу тела — это согласуется с «один раз на тысячу запусков».

### 5. Вариант фикса для HTTP-режима (`chfix`)

`chfix.Apply(opt)` подключается через штатный `Options.DialContext` (без форка и без
обёртки над драйвером) и ставит новый дедлайн перед каждым чтением и каждой записью
сокета, равный `ReadTimeout`. Операция, которая не продвигается дольше таймаута,
завершается `i/o timeout`.

```go
opt := &clickhouse.Options{Protocol: clickhouse.HTTP, ReadTimeout: 2 * time.Second /* … */}
chfix.Apply(opt)
conn, err := clickhouse.Open(opt)
```

Повтор HTTP-матрицы без дедлайна в контексте (`./bin/chmatrix matrix -fix -ctx none`, 74 случая):

| | без фикса | с `chfix` |
|---|---|---|
| зависших случаев | 16 | 2 |
| потеря пакетов / заморозка сервера, чтение тела | висит | 2,0 с |
| потеря пакетов / заморозка сервера / 1 КБ/с, запись INSERT | висит | ≤ 2,6 с |
| `SELECT 1`, обрыв между заголовками и телом | висит | 2,0 с |
| канал 1 КБ/с, чтение тела | висит | **висит** |
| контроль без сбоев (ping, INSERT 48 МБ) | успех | успех |

Сценарий инцидента с фиксом (`./incident.sh nft-drop stream 30 0 true`): итерация
реплики A падает через 2 с и отпускает блокировку, реплика B продолжает работу.

Ограничения:

- это таймаут простоя, а не общий таймаут запроса: медленно капающий ответ (1 КБ/с)
  он не обрывает — два оставшихся зависших случая именно такие; общий срок задаёт
  только дедлайн в `context`;
- легитимный ответ с паузой между блоками дольше `ReadTimeout` теперь обрывается
  (контроль `select-slow-body`: 2,0 с, ошибка) — так же ведёт себя нативный протокол;
- простаивающее keep-alive соединение закрывается через `ReadTimeout` и
  переустанавливается при следующем запросе.

## Что из этого следует

1. Дедлайн в `context` на каждый вызов ClickHouse — единственное, что в этих тестах
   ограничило все фазы в обоих протоколах. `chfix` закрывает зависания при пропавшем
   соединении, но не заменяет его.
2. Нативный протокол закрывает чтение, но не запись большого INSERT; кроме того, его
   `ReadTimeout` обрывает и легитимные запросы с паузами между блоками длиннее таймаута.
3. Блокировка в Postgres, которую держат на время сетевого вызова без дедлайна, превращает
   зависание одного клиента в остановку всех реплик. На стороне Postgres/PgBouncer здесь
   не было ни `lock_timeout`, ни `idle_in_transaction_session_timeout`, ни `idle_transaction_timeout`.
4. Readiness через тот же пул из одного соединения показывает «не готов» при любой
   долгой операции, а не только при недоступности базы.

## Чего стенд не проверял

- TLS (у `http.Transport` в clickhouse-go не задан `TLSHandshakeTimeout`).
- Сбой на участке приложение ↔ PgBouncer и PgBouncer ↔ Postgres.
- Какой именно из механизмов сработал в production: стенд показывает, какие возможны.
